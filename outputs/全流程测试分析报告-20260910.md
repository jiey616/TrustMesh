## 三、缺陷根因分析（根因链 + 证据）

### 🔴 BUG-01：顺序自动派发断链后被静默吞掉（P0）

**这是你问的「TD03 执行完了之后没推进到 TD04」的直接原因。**

#### 证据

| 证据 | 内容 |
|---|---|
| 事件审计 | 全程 `todo_assigned` 共 6 条，**5 条 `manual=false`（系统自动派发）**，唯独 TD_04 是 `manual=true`（`test001@163.com 手动派发给 资产制作师`） |
| 排除审核门 | 任务内 `review` 类事件 **0 条**，排除「need_review 待人工审批阻塞」的可能 |
| 排除前序未完成 | TD_03 于 21:48:27 正确写入 `todo_completed` + `status=done` |
| 排除额度/停用问题 | 该项目未归档，后续 TD_05/TD_06 自动派发均正常 |

```
10:05:55Z | actor=System         | 按顺序派发给 编剧      | manual=false
11:04:37Z | actor=System         | 按顺序派发给 分镜师    | manual=false
12:38:10Z | actor=System         | 按顺序派发给 导演      | manual=false
13:48:27Z | （缺失 — 应自动派发 TD_04，但无任何事件）
14:44:57Z | actor=test001@163.com| 手动派发给 资产制作师  | manual=true   ← 用户等待 56 分钟后补救
14:57:17Z | actor=System         | 按顺序派发给 分镜师    | manual=false
22:56:21Z | actor=System         | 按顺序派发给 视频制作师| manual=false
```

#### 根因链

```
导演回报 todo.complete
   └─> webhook.handleTodoComplete
        └─> CompleteTodoByNodeWithMessageID（✅ 正常落库，TD_03 -> done）
             └─> dispatchNextTodo()               ← 断点在这里
                  └─> task.NextDispatchableTodo() ✅ 正常返回 TD_04
                       └─> client.Publish(NATS)   ❌ 失败/不可用
                            └─> log.Warn(...) + return task   ← 静默终止
```

**源码定位**：`backend/internal/clawsynapse/webhook.go:1789-1826`

```go
func (h *WebhookHandler) dispatchNextTodo(ctx context.Context, task *model.TaskDetail) *model.TaskDetail {
	if h == nil || task == nil || h.client == nil {
		return task          // ← 静默路径 ①：NATS client 未就绪
	}
	todo := task.NextDispatchableTodo()
	if todo == nil { return task }
	if appErr := h.store.CheckTaskProjectActive(task.ID); appErr != nil {
		h.log.Warn(...)
		return task          // ← 静默路径 ②
	}
	if _, err := h.client.Publish(ctx, todo.Assignee.NodeID, "todo.assigned", ...); err != nil {
		h.log.Warn(...)      // ← 静默路径 ③：只打 WARN，无重试、无事件、无通知
		return task
	}
	updatedTask, appErr := h.store.RecordSequentialTodoDispatch(task.ID, todo.ID)
	if appErr != nil {
		h.log.Warn(...)
		return task          // ← 静默路径 ④
	}
	return updatedTask
}
```

**四条静默退出路径无一例外：** 不重试、不落失败事件、不改任务状态、不通知用户。todo 停在 `pending`，任务停在 `in_progress`，界面上看不出任何异常——只有一条 WARN 日志。

**佐证**：`internal/clawsynapse/client.go` 全文检索 `retry|Retry|backoff` **零命中** → `Client.Publish` 确认无重试。这与项目记忆里已记录的「转发节点 DeliverMessage 零重试」是同一类问题在派发链路上的复现。

> ⚠️ **置信度说明**：后端容器已于调查前重启，21:48:27 左右的原始 WARN 日志已随容器日志轮转丢失，无法取得「publish error」的直接文本。以上为基于事件审计（缺 `todo_assigned`）+ 源码路径推演得出的**高置信推断**。

### 🔴 BUG-02：超时重试计数器被 agent 评论反复归零（P0）

**这是 TD_05「8 小时卡死而不判失败」的根因，也是本次最严重的系统性缺陷。**

#### 证据

| 证据 | 内容 |
|---|---|
| TD_05 提醒次数 | **14 次** `todo_timeout_remind`，跨度 7 小时 59 分 |
| 提醒计数字段 | 18 次提醒（含其他 todo）中 **全部 `remind_count=1 / max=3`** |
| 全库统计 | 115 条提醒事件中 **103 条 `remind_count=1`（89.6%）**，仅 9 条=2、3 条=3 |
| 受影响任务 | 全库 **13 个任务**出现过 ≥3 次提醒，最高 20 次 |

`defaultMaxReminders = 3`，理论上第 3 次提醒后无响应就该判失败。但 `remind_count` 永远停在 1 → **`todo.RemindCount >= maxReminders` 这个判失败条件从未成立过**。

#### 根因链

```
平台：30 分钟无进展 → 发 todo_timeout_remind（RemindCount 0→1）
   ↓
提醒使 agent runtime 报错，agent 把错误当普通 comment 回报
（本例中：⚠️【执行侧故障上报】hermes run failed: ...）
   ↓
addTaskComment 路径无条件重置：RemindCount = 0 / RemindAt = nil / LastActivityAt = now
   ↓
超时计时归零 → 回到第 1 步，无限循环
```

**源码定位**：`backend/internal/store/workflow.go:1196-1201`（`AddTaskCommentByNode`）

```go
for i := range task.Todos {
	td := &task.Todos[i]
	if td.Status != "in_progress" || td.Assignee.AgentID != agent.ID {
		continue
	}
	td.LastActivityAt = &now
	td.RemindCount = 0      // ← 🔴 BUG：纯错误报告也被当成「有效活动」
	td.RemindAt = nil
}
```

**同一个「任意活动即视为存活」的语义还分布在另外 5 处**：`UpdateTodoProgressByNode`(L666)、`CompleteTodoByNodeWithMessageID`(L744)、`AskTodoByNode`(L888)、`AnswerTodo`(L966)、`FailTodoByNodeWithMessageID`(L1130)。

> 一个正在持续崩溃并不断上报故障的 agent，被系统判定为「一直很活跃」，于是永不判失败。**这是一个典型的 liveness 误判**。

## 五、修复建议（按优先级）

| 优先级 | 修复项 | 具体做法 | 源码位置 |
|---|---|---|---|
| **P0** | 派发失败不再静默 | ① `Publish` 加 3 次指数退避重试；② 仍失败则落 `todo_dispatch_failed` 事件 + 用户通知；③ 失败时把 todo/task 显式置为 `dispatch_blocked`，界面可见 | `webhook.go:1789-1826`、`client.go:316` |
| **P0** | 修正 liveness 语义 | 只有 `todo.progress` / `todo.complete` 这类**正向进展**才重置 `RemindCount` 与 `LastActivityAt`；`task_comment`、**尤其是匹配 `故障上报/【.*故障` 前缀的错误类评论不参与续命** | `workflow.go:1196-1201` 等 6 处 |
| **P0** | 加固判失败 | 增加「挂钟上限」硬闸：todo 从 `started_at` 起超过 N 小时无论是否有活动一律判失败（建议 N = 4h，可按 todo 级配置） | `timeout_monitor.go:96-135` |
| **P1** | 终态后回补通道 | 提供 `POST /tasks/:id/todos/:todoId/reopen`，支持把 terminated todo 回退重开并回收终态后产物；或至少把终态后产物标 orphan | `handler/task.go` / `store/workflow.go` |
| **P2** | 减少冗余上传 | 上传接口在缺 `outputName` 时，若该 todo 有唯一输出位则**自动绑定并提示**，而非强制 agent 重传；加 fingerprint 去重抑制重复 artifact | 上传 handler |

**建议的验证方式**：修完后重跑同一条工作流（同一 project），断言：
1. 全程 `todo_assigned` **6/6 均为 `manual=false`**，且相邻 todo 间隔 < 5 秒；
2. 注入一次 NATS 不可用（停 `trustmesh-clawsynapse` 30 秒），验证能**落 `todo_dispatch_failed` 事件并恢复自动派发**；
3. 让一个 todo 持续报错 1 小时，验证 **4 小时内必判 failed**，且 `remind_count` 能走到 ≥3。

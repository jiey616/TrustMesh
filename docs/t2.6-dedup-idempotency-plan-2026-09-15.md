> 批次：阶段 2 第 5 批（收口 T2.1/T2.2/T2.3b 遗留的「无幂等键」代价；派发去重经复核 descoped，见 §3.3/§8）
> as-built：本批**只交付「会议消息幂等」**；原计划的「派发幂等」在实施后经预审复核否决并回退（descoped），详见 §3.3 与 §8。
> 日期：2026-09-15
> 关联：T2.1 §已知代价（P2-2 会议消息无幂等键）、T2.2/T2.3b「写路径仍无幂等键 → T2.6」、T3.1 硬依赖 T0.9+T2.6

## 1. 目标与范围

**目标**：在 store 层引入一个**通用、Mongo 支撑、带 TTL 的幂等键存储**，消除两类重复写入：

1. **客户端超时重试导致的重复**（inbound）：主要是 `AddMeetingMessage`（会议消息），目前每次 `uuid.NewString()` 生成新 ID，重试必重复入库。
2. **多实例派发重复**（cross-instance，T3.1 前置）——**本批 descoped（不纳入）**：同一 task/todo 派发被多个 backend 实例各自处理。曾拟用「派发幂等键」兜住，实施后经复核否决并回退：① 派发 publish 在 store 记录之前，store 层键防不住双派；② 真防双派属 **publish 层租约**，归 T3.1/T0.9；③ 跨实例「提升」去重其实已由 T2.x 乐观锁（`mutateTaskUnsafe` 的 version filter）覆盖，该键冗余且净负面。详见 §3.3、§8。

**范围**（as-built：派发不纳入，见 §3.3/§8）：

- ✅ 新增 `idempotency_keys` Mongo 集合（`_id` 天然唯一 + TTL 索引 `expire_at`）+ 内存 LRU 快路径 `s.idemCache`。
- ✅ 通用原语 `idemCheckOrRecord(key, ttl) (seen bool, err)`。
- ✅ 应用到：
  - `AddMeetingMessage`（会议消息，闭合 T2.1 P2-2 已知代价）。
- ✅ 测试门禁：`-race` + 活库双写探针（同键两次 → 第二次返回首结果、库内仅 1 条）。

**不做（明确划出）**：

- ❌ **派发不纳入（descoped）**：不在 `RecordSequentialTodoDispatch` / `RetryDispatch` 加幂等守卫。理由见 §3.3/§8。
- ❌ 不动 `opsByDedupeKey`（ops 工单去重已是 Mongo 部分唯一索引，独立机制，不在本批）。
- ❌ 不动 `processedMessages`（planning 的 `task.plan_ready` 等已幂等，保留；本批不强制迁移，但 `idemCheckOrRecord` 可作为其通用替身，留给后续清理）。
- ❌ 不动 clawsynapse 侧 NATS 消费（agent 派发在另一个仓库）。
- ❌ 不实现 T3.1 多实例本身（仍硬依赖 T0.9 NATS 隔离 + publish 层租约）。

## 3. 设计方案（选项 A，推荐）

### 3.1 通用幂等键存储
- 新增 Mongo 集合 `idempotency_keys`，文档 `{ key: string, expire_at: time.Time }`：
  - 唯一索引 `{ key: 1 }`（E11000 = 已存在 = 命中）。
  - TTL 索引 `{ expire_at: 1 }`（自动过期，避免无限增长；默认 TTL 24h，会议消息可短至 5m）。
- 内存快路径 `s.idemCache map[string]time.Time`（`cleanup.go` 复用 `maxProcessedMessages` 上限做 LRU 淘汰），减少热路径 Mongo 往返。
- 原语：
  ```go
  // 返回 seen=true 表示键已存在（应跳过/返回首结果）；seen=false 表示首次并已完成记录。
  func (s *Store) idemCheckOrRecord(key string, ttl time.Duration) (seen bool, err *transport.AppError)
  ```
  实现（持 `s.mu` 内调用，或内部自取轻量锁）：
  1. 快路径：键在 `idemCache` 且未过期 → `seen=true`。
  2. 慢路径：`idempotency_keys.InsertOne({key, expire_at: now+ttl})`：
     - 成功 → 写入 `idemCache`、`seen=false`。
     - `E11000`（dup）→ `seen=true`（不报错）。
     - 其他 Mongo 错 → 按 `mongoWriteError` 返回（**宁可失败也不静默放行重复**，与 T2.x「致命化」一致）。
  3. Mongo 未启用时：仅用 `idemCache`（退化为内存语义，与现状等价，不阻断）。

### 3.2 应用到 `AddMeetingMessage`
- 入参 `model.MeetingMessage` 增加可选字段 `IdempotencyKey string`（客户端超时重试带同一键；不带的旧客户端由 backend 派生 `meetingID|senderType|senderID|contentSHA|±window` 软键）。
- 在 L395 写序之前插入：`seen, err := s.idemCheckOrRecord(key, 5*time.Minute)`；`seen` → 返回已存消息（查库或缓存）并跳过落库；`err` → 返 5xx。
- 闭合 T2.1 P2-2 已知代价；不影响现有 SSE / 会话态派生逻辑。

### 3.3 应用到派发入口 —— **派发不纳入（descoped）**
- 原计划：`RecordSequentialTodoDispatch` / `RetryDispatch` 提升前 `idemCheckOrRecord("dispatch|taskID|todoID|nodeID", 24h)`；`seen` → 直接返回当前态、不重复提升。
- **实施后复核否决并回退**（`workflow.go` 已恢复原逻辑）：
  1. **publish 在守卫之前**：两条派发路径都是「先 publish 到 agent、后 `RecordSequentialTodoDispatch`」（首次 `webhook.go:2187→2197`；对账重派 `webhook.go:2324→2328`，正是 `RetryDispatch` → 挂守卫的那个入口）。守卫在 publish **之后**，**防不住多实例双派** → 未达成 T3.1 目标。
  2. **净负面**：若「提升」的 persist 失败（`mutateTaskUnsafe` 回滚内存 → todo 仍 `pending`）但幂等键已落（TTL 24h），对账器每 2 分钟重发、`RecordSequentialTodoDispatch` 恒 `seen` → **永不提升 → todo 卡死 `pending` + agent 重复派发风暴**（Mongo 恢复后仍卡至 TTL 过期）。
  3. **冗余**：跨实例「提升」去重**已由 T2.x 乐观锁提供**（`mutateTaskUnsafe` → `applyTaskVersionedReplaceLocked` 的 version filter；第二实例版本冲突、不双提升）。
- 结论：真防「双派」属 **publish 层租约**（agent 侧 publish 前取租约），归 T3.1/T0.9；store 层幂等键在此位置既无效又危险，故 descope。

### 3.4 与 T2.5 的关系
- 本批不改锁粒度（锁仍是全局 `s.mu`）；`idemCheckOrRecord` 在持锁内做 Mongo I/O，**会短暂拉长临界区**（一次 InsertOne，≤ MONGO_TIMEOUT）。这是已知代价，留 T2.5 拆锁时一并处理（或本批用「释放 s.mu 后再 InsertOne、用版本/键唯一兜底」的折中，见选项 C 风险）。
- 推荐 A 保持简单：幂等键 InsertOne 直接在现有持锁上下文内（与 `AddMeetingMessage` 已有两次 Mongo 写同序），不引入新的锁编排风险。

## 7. 风险与回滚
- **风险 1（临界区）**：`idemCheckOrRecord` 的 InsertOne 在 `s.mu` 内 → 临界区 +1 次 Mongo 写。 mitigated：InsertOne 极快、TTL 索引后台清理；T2.5 拆锁时彻底解。
- **风险 2（TTL 过短丢重）**：会议消息 TTL=5m 内重试去重，超过窗口允许重复（业务可接受，聊天重发不致命）。
- **风险 3（Mongo 抖动）**：InsertOne 失败按 `mongoWriteError` 致命化 → 宁可 5xx 不静默重复（对齐 T2.x）。
- **回滚**：`idemCheckOrRecord` 为纯新增、调用点可一行回退；集合 `idempotency_keys` 无业务数据、删除即净。回滚锚 `20260915-143730`（T2.x 全量 backend）仍留生产。

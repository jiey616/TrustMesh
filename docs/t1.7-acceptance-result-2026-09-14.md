## 2. 认证阻塞根因（本次关键突破）

此前所有带 JWT 的受保护接口都返回 `UNAUTHORIZED / missing or invalid authorization header`，即使换真/假 token 都返回**同一前缀错误**——证明 header 根本没带 `bearer ` 前缀到达中间件。

**根因**：Windows PowerShell 以 `ssh host $cmd` 数组参数传命令时，对 `-H "Authorization: Bearer $tok"` 做了按空格分词，curl 实际只收到残缺的 `-H Authorization:`，`Bearer` 段被拆成多余参数 → header 失效。

**绕过（已验证可靠）**：
1. 把整段远程脚本写成 LF 纯文本文件（Write 工具默认 CRLF，须用 PS `.NET` 写入器转 LF，否则 `bash -s` 因 `\r` 报 `syntax error`）。
2. `Get-Content -Raw <lf脚本> | ssh ... 'bash -s'` 整段以 stdin 喂给远端 bash——PowerShell 不做分词，引号完整保留。
3. 带 body 的请求改用远端文件 `curl -d @/tmp/body.json`（用 `printf '%s' '<单引号JSON>'` 落盘），彻底避开空格分词。

> ⚠️ 安全策略禁止在 PowerShell 里 `tr -d "\r" | bash -s` 这类非 PowerShell shell 管道（会触发 "Spawning a non-PowerShell shell" 拦截）。LF 转换必须在本地用 `.NET` 完成。

## 4. 与计划 canary 表的偏差（均已安全，记录备查）

- **非存在租户（6d）返回 401 而非 404**：`GET /projects` 带 `X-Org-Id` 时中间件先查"是否成员"，非成员直接 401，不区分 org 是否存在。无 200+空数组、无越权，红线仍满足。
- **`GET /organizations/:id` 对 non-member 返回 404**（对称隔离 B），而 `GET /projects + X-Org-Id` 对 non-member 返回 401（6c/D）。两条路径的门禁措辞不同（404=不可见 / 401=非成员），但都安全，无泄露。
- **建项目被 `pm_agent_id` 必填挡住**：这是真实产品约束（`store_project.go:86` 判空 + `:97 pmAgentForScopeUnsafe` 校验 agent 归属）。新企业无 agent 即无法建项目——本质是 G7（agent 入企）前置依赖。

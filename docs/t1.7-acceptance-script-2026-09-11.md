## 1. 新鲜租户定义

- **第二用户 U2**：新邮箱（如 `t17-member@<domain>`）**自助注册**，注册后自动生成个人租户 `OrgU2(personal)`，U2 为其 Owner，返回 JWT。
- **第二企业 Org2**：新 slug（如 `t17-acceptance-<ts>`），由 U2 经 `POST /organizations`（`handler/organization.go:114`）创建，U2 成为 Owner。
- **独立性要求**：U2 的 user_id / Org2 的 org_id 与现有生产租户（`test001` 个人空间 `org_6a9ad805`、`画宗` 企业 `org_d15fa58a`）**完全不同**；不共享任何项目/agent/会议/任务。
- **从零建企业可行性**：已核实 `POST /organizations`（建者成 Owner）+ 前端 `OrgSettingsPage.tsx:106` 可用。

## 2. 7 步全流程验收

> 每步给出：操作方 / 操作动作 / 可观测预期结果 / 取证方式 / 通过判据 / 真实支持度与缺口。
> 所有写操作只允许落在 U2 / Org2 的 ID 范围内（见 §6 安全约束）。

### 步骤 1 · 代建账号（产品缺口 + 验收替代路径）

- **操作方**：第二用户（自助）
- **操作动作**：打开 `RegisterPage` → 用新邮箱注册 → `POST /api/v1/auth/register`（`router.go:116`）
- **可观测预期结果**：注册成功，自动生成个人租户（`kind=personal`），U2 成为其 Owner，返回 JWT
- **取证方式**：① 接口返回 `200` + `user` + `token`；② DB `users` 新增 1 行；③ `organizations` 新增 1 条 `kind=personal`；④ `org_memberships` 新增 1 条（U2→个人租户，role=owner）
- **通过判据**：U2 可登录、个人租户存在、JWT 可调用受保护接口
- **真实支持度 / 缺口**：⚠️ **MISSING**——无 admin/平台代建账号端点（无发放账号、无初始密码途径）。**验收替代**：以自助注册完成第二账号创建。**记录产品缺口 G1**（见 §5）。

### 步骤 2 · 邀请（按 email 加已注册成员 + 缺口）

- **操作方**：Owner（U2，对自建的 Org2）
- **操作动作**：在企业管理页「成员管理」用「按 email 加成员」入口（`OrgSettingsPage.tsx:266`）→ `POST /api/v1/organizations/:id/members`（body `email=U2 邮箱`，`handler/organization.go:175 AddMember`）
- **可观测预期结果**：U2 成为 Org2 成员（默认 role=member）
- **取证方式**：① 接口 `200`；② DB `org_memberships` 新增（org_id=Org2, user_id=U2, role=member）；③ 前端成员列表出现 U2
- **通过判据**：以 Org2 上下文（`X-Org-Id: Org2`）查询企业内资源，U2 可见
- **真实支持度 / 缺口**：⚠️ **PARTIAL**——无邀请码/邀请链接，只能「按邮箱拉**已注册**账号」。**记录产品缺口 G2**（见 §5）。冷启动只能邀请已注册账号。

### 步骤 3 · 审批入企（agent 节点 join request，EXISTS）

- **操作方**：Owner / admin
- **操作动作**：让一个 agent 节点对 Org2 发起 join（auth challenge + trust request）→ 生成 JoinRequest → Owner 在 `AgentInvitePage.tsx:197` 审批 `POST /api/v1/agents/join-requests/:id/approve`（`handler/join_request.go:165`）
- **可观测预期结果**：审批受 owner/admin 门禁（`store/store_join_request.go:288-291`）；非 owner/admin 调用 → `403 Forbidden`；通过后 agent.OrgID = Org2
- **取证方式**：① owner 审批 `200`、非 owner 审批 `403`；② DB `agents` 对应记录 `OrgID=Org2`；③ `org_memberships` 中该 agent 节点归属 Org2
- **通过判据**：仅 owner/admin 可审批；通过后 agent 归属 Org2
- **真实支持度 / 缺口**：✅ **EXISTS**。备注：需一个**空闲/新建 agent 节点**用于演示入企审批——若当前无空闲节点，本条依赖基础设施准备（**待核实**：是否有可用于冷启动的 agent 节点 / 容器）。当前 `TRUSTMESH_STRICT_DISPATCH_ORG_GATE` 默认 OFF（观测态），不影响审批本身；若后续翻 true，需先跑 `deploy/migrate_agent_org_bind.py`。

### 步骤 4 · 跨成员共享 agent（org 级共享，PARTIAL）

- **操作方**：Org2 成员（U2 或另一成员）
- **操作动作**：在 Org2 工作区招募/创建一个 agent → 其 `OrgID` 自动 = Org2（`store/store_agent.go:54`）；Org2 内任意成员查看 agent 列表
- **可观测预期结果**：agent 对 Org2 全体成员可见、可被指派；`visibleToScope`（同 org）裁决生效
- **取证方式**：① 任意 Org2 成员带 `X-Org-Id: Org2` 查 `/agents` 可见该 agent；② DB `agents.OrgID=Org2`
- **通过判据**：同 org 成员共享可见、可指派；切换非本 org 成员视角不可见
- **真实支持度 / 缺口**：⚠️ **PARTIAL**——仅 **org 级**共享（一个 agent 对全员可见），**无「按指定成员单独授权/白名单」**能力（visibility 白名单字段仅 `external_app` 有）。**记录产品缺口 G3**（见 §5）。对冷启动验收不构成阻塞（全员共享即满足），但需在报告标注能力边界。

### 步骤 5 · 跨成员建项目 / 会议 / 任务（EXISTS）

- **操作方**：Org2 成员
- **操作动作**：在 Org2 工作区下依次创建 ① 项目 `POST /projects`（`router.go:159`）② 会议 `POST /projects/:projectId/meetings`（`router.go:296`）③ 任务 `POST /projects/:projectId/tasks`（`router.go:305`）；归属通过 `resolveOwnerOrgUnsafe`（挂 active org，`store/scope.go:61`）
- **可观测预期结果**：资源创建成功且 `org_id=Org2`；带 `X-Org-Id: Org2` 的成员均可访问（私有项目可再加成员白名单 `store/store_org.go:214`）
- **取证方式**：① 三个创建接口均 `200`；② DB 对应记录 `org_id=Org2`；③ 另一 Org2 成员带同租户头可读取
- **通过判据**：资源创建成功、归属 Org2、同 org 成员可见
- **真实支持度 / 缺口**：✅ **EXISTS**。备注：任务若进入 agent 派发路径，受 `TRUSTMESH_STRICT_DISPATCH_ORG_GATE`（默认 OFF）影响——当前观测态不阻断；本步骤验收的是「创建与归属」，派发生效以步骤 3/4 的 agent 归属为前提。

### 步骤 6 · 切换企业 + 数据隔离（EXISTS）

- **操作方**：U2（在前端切换工作区）+ 验收脚本（跨租户对照）
- **操作动作**：① 前端通过租户切换器（`MainLayout.tsx:150-197` / `ProfilePage.tsx:172-220`）切到 Org2，每请求带 `X-Org-Id: Org2`；② 隔离对照见 §3
- **可观测预期结果**：切到 Org2 后只见 Org2 数据；对 test001 生产租户数据完全不可见
- **取证方式**：见 §3 隔离判定表（接口返回码 + DB 计数）
- **通过判据**：① 带 Org2 头查询只返回 Org2 数据；② 伪造生产租户头 → 401/404；③ **绝不出现 200+空数组**
- **真实支持度 / 缺口**：✅ **EXISTS**（隔离由 `middleware/org_scope.go` 常驻生效，与 STRICT 门禁无关）

### 步骤 7 · 配额展示（EXISTS 但仅展示、无强制）

- **操作方**：Owner（U2）
- **操作动作**：打开企业管理「配额」区（`OrgSettingsPage.tsx:320-323`）查看成员/节点/项目/存储上限；调 `GET /organizations/:id`（`router.go:375` → `handler/organization.go:141`）
- **可观测预期结果**：正确展示 `OrgQuota`（默认全 `-1` 显示「不限」）
- **取证方式**：① 前端展示值与 `GET /organizations/:id` 返回的 `quota` 一致；② DB `organizations.quota` 存在
- **通过判据**：展示正确、与接口一致
- **真实支持度 / 缺口**：⚠️ **EXISTS 但仅展示**——`MaxMembers/MaxNodes/MaxProjects/MaxStorageBytes` 在生产代码中**无强制校验点**（全仓 grep 仅命中 model + 1 处测试）。**记录产品缺口 G4**（见 §5）。⛔ **不得写成"配额生效拦截"**——本次仅验收展示正确性，不验收强制。

## 3. 数据隔离判定法（隔离 canary）

用 **test001 现有生产数据作诱饵**（已知：个人空间 `org_6a9ad805` 有 projects=5、agents=6，见迁移文档 §1.2/§2.2；`画宗` 企业 `org_d15fa58a` 当前 0 条）。验收时：

| 场景 | 请求 | 预期结果 | 判据含义 |
|---|---|---|---|
| 干净租户视图 | U2 + `X-Org-Id: Org2` → `GET /projects` | 返回 **Org2 自有**数据（0 或新建 N 条） | 不含 test001 的 5 条 |
| 生产租户不受影响 | test001 原 token → `GET /projects` | 仍返回 **5 条** | 现有生产租户未被改动 |
| 跨租户越权 | 伪造 `X-Org-Id: org_6a9ad805`（test001 个人空间）非成员访问 | **401** | 非成员带租户头越权拦截 |
| 不存在的租户 | `X-Org-Id: org_nonexistent` | **404**（绝不 200+空） | 不可见 = 不存在，防存在性泄露 |
| 权限不足 | 非 owner/admin 审批/改成员 | **403** | 权限不足拦截 |

**红线**：任何接口**绝不返回 200 + 空数组**作为「不可见」的表达——那等于隔离失效。正确表达是 401/403/404。

## 6. 失败与回滚的业务要求（🔴 不得影响现有生产租户）

1. **范围锁死**：所有写操作只允许落在 `U2` / `Org2` 的 ID 范围内。test001 个人空间（`org_6a9ad805`）与 `画宗` 企业（`org_d15fa58a`）**只做读取对照（canary），绝不写入/改写**。
2. **不改动生产数据**：不因验收触发 `updateMany`/回填任何生产集合（迁移文档 §三 的 org_id 回填是另一独立任务，不在本验收内）。
3. **清理路径（待核实）**：若需撤销，优先「保留空壳」策略（仿迁移文档决策 D2）——保留 U2 个人空间空壳 + Org2 空企业，可逆、零成本；**删除 API 是否可用待核实**（无把握则不删，只停用/保留）。
4. **配额无强制**：G4 状态下不会因超限拦截，回滚风险低；但对外开放前必须补 G4 强制校验（见 §5）。
5. **STRICT 门禁**：验收期间保持默认 OFF 即可（观测态），不临时翻转生产 `TRUSTMESH_STRICT_*` 以免误伤。
6. **JWT 失效**：重启/重登后旧 token 失效，验收脚本每次操作前重新登录取 token（仿迁移文档 R3）。

## 7. 验收通过总判据

✅ **通过**：步骤 1–7 全部以「真实第二租户」走通；步骤 6 隔离 canary 全部命中 401/403/404 且**无 200+空数组**；产品 KPI「冷启动一次跑通率 = 100%（或带 G1/G2 替代路径明确记录）」。

❌ **不通过**：任意跨租户数据泄露（200+空数组 或 返回他租户数据）、或 Owner/Admin 门禁可被绕过（非 owner 审批成功、非成员带头读到他租户数据）。

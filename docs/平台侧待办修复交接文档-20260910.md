## 2. 前置必读（违反会导致静默失败）

### 2.1 🔴 CRLF 陷阱

仓库**全部文件为 CRLF**，且**基线 `gofmt` 不干净**（`client.go` 字段对齐、`task.go` OrgID 对齐等既有问题）。

- **禁止** `gofmt -w` / `goimports -w` 全文件覆盖 → 会把整个文件行尾翻转成 LF，产生巨量无意义 diff。
- 新增代码请**手写对齐**（tab 对齐字段列），或只对**新增的小文件**跑 gofmt。
- 编辑既有文件建议用**精确字符串替换**，不要整文件重写。

### 2.2 🔴 后端是构建式部署

改动 Go 代码后必须重建镜像，不是热加载：

```
docker-compose build backend
docker-compose stop backend      # 注意：先 stop
（轮询直到容器 exited）
docker-compose rm -f backend
docker-compose up -d backend
```

- 容器名 `trustmesh-backend`；验收必须看到 `healthy`。
- 端口/路由：登录是 **`/api/v1/auth/login`**（不是 `/v1`）。

### 2.3 编译工具

本机**无 Go 工具链**，用 Docker 临时容器编译，并走命名卷缓存（避免每次重下依赖）：

```
docker run --rm -v <repo>:/src -v trustmesh-gocache:/go/pkg/mod -w /src/backend golang:1.25 go build ./...
```

### 2.4 提交要求

1. 单个 commit 只做一项 FIX，message：`fix(<scope>): <ID> <一句话>`。
2. 必须带单元测试（测试名见各项验收标准）。
3. 改完跑：`go build ./...` + `go vet` + `go test ./internal/store/ ./internal/clawsynapse/ ./internal/app/`。
4. `git add` **按路径精确 add**，**禁止** `git add -A`。

> ⚠️ 当前仓库有 **290 个未提交改动**（含 `frontend-v2/`）。开工前**必须先与负责人确认提交策略**，不要顺手把无关改动一起提交。

## 3. P-04 步骤 2：下载令牌错误码区分 + 补救指引 🟡 P1

### 现状

`internal/agentfile/agentfile.go:172`：

```go
transport.WriteError(c, transport.Unauthorized("invalid or expired download token"))
```

**「无效」与「过期」混为一谈**，且不给补救指引。Agent 无从得知应该重新 `task.context.query` 取新链接，会把可恢复错误当致命阻塞而误判 todo 失败（2026-09-10 TD_06）。

> 注：P-04「TTL 过短」的根因**已被推翻**（现网本就是 24h）。本步骤与 TTL 数值无关，解决的是**错误语义**。

### 改动

`internal/agentfile/agentfile.go` 第 165–174 行附近改为：

```go
	claims, err := h.jwtMgr.ParseToken(token)
	if err != nil {
		// 区分「过期」与「无效」：过期是可恢复的，指引 agent 重新取链接，
		// 避免它把可恢复错误当成致命阻塞而误判 todo 失败（2026-09-10 TD_06）。
		if errors.Is(err, jwt.ErrTokenExpired) {
			transport.WriteError(c, transport.Unauthorized(
				"DOWNLOAD_TOKEN_EXPIRED: 下载令牌已过期，请重新调用 task.context.query 获取新的 download_url 后重试"))
			return
		}
		transport.WriteError(c, transport.Unauthorized("invalid download token"))
		return
	}
```

- 需 import `errors` 与 `github.com/golang-jwt/jwt/v5`（按仓库实际 jwt 库调整 `ErrTokenExpired` 引用）。
- **必须实测确认**底层库在过期时确实返回可被 `errors.Is` 命中的 `ErrTokenExpired`；若库版本不同，改用其对应哨兵错误。

### 可选（P2，建议做但要先确认）

**步骤 3**：新增 `POST /api/v1/agent-files/:fileId/refresh-url`，agent 持任务上下文即可重取，不必走完整 `task.context.query`。

### 配套（非本文范围）

节点侧 skill 必须写明「`DOWNLOAD_TOKEN_EXPIRED` → 先重取链接再重试，至少 3 次」——对应节点文档 **N-06**。两端一起才闭环。

## 4. P-05 ｜ 终态后无状态回补通道 🟡 P1

### 根因

TD_06 在 23:08 被判 `failed`，但 agent 在 23:12 后**实际完成了 4/6 组视频**并于 00:08:32 上传台账、成功绑定输出位 → 形成「**failed todo 挂 done 交付物**」的不一致。平台**没有任何「终态后完成」的回补路径**。


### 改动

#### 步骤 1：新增 reopen 接口

**路由**（`internal/app/router.go`，authed 组，紧随既有 todo 子路由，参考 283–290 行）：

```go
authed.POST("/tasks/:id/todos/:todoId/reopen", taskHandler.ReopenTodo)
```

**Handler**：`internal/handler/task.go` 新增 `ReopenTodo`（照抄同文件既有 `ReviewTodo`/`DispatchTodo` 的参数解析与错误返回风格）。

**Store**：`internal/store/workflow.go` 新增 `ReopenTodo(sc Scope, taskID, todoID, reason string)`。

Store 逻辑要点：

```go
	// 仅允许从终态回退（failed / canceled / done）
	if todo.Status != "failed" && todo.Status != "canceled" && todo.Status != "done" {
		return nil, transport.Conflict("TODO_NOT_TERMINAL", "只有已结束的 todo 可以重开")
	}
	if todo.ReopenCount >= maxReopens {          // 新常量，默认 3
		return nil, transport.Conflict("TODO_REOPEN_LIMIT", "重开次数已达上限")
	}
	todo.Status = "in_progress"
	todo.FailedAt = nil
	todo.CanceledAt = nil
	todo.CompletedAt = nil
	todo.Error = nil
	todo.RemindCount = 0
	todo.RemindAt = nil
	now := time.Now().UTC()
	todo.LastProgressAt = &now
	todo.LastActivityAt = &now
	todo.ReopenCount++
	// 落事件 todo_reopened（含 reason）
```

**模型新增**（`internal/model/task.go`，`Todo` 结构体，参考 `RetryCount`/`RemindCount` 一带）：

```go
	// ReopenCount counts how many times a terminal todo was reopened, so a
	// failed step whose agent actually finished late can be recovered without
	// letting a loop reopen it forever.
	ReopenCount int `json:"reopen_count" bson:"reopen_count"`
```

**事件命名对齐**：既有事件采用 `todo_*` 蛇形（`todo_completed` / `todo_failed` / `todo_dispatch_failed` / `todo_hard_deadline_failed`），故用 **`todo_reopened`**。

> `internal/model/ops.go:59` 已有 `OpsActionReopened = "reopened"` 常量，但那是**运维工单动作**，与 todo 事件不是一回事，不要复用。

#### 步骤 2：终态后到达的产物显式标记

现有逻辑（`store_artifact.go:246`）在 `todo.Status == "done" && taskArtifactsClosed(task.Status)` 时**直接拒绝**（`TODO_ALREADY_DONE`）。

改为：**仍允许绑定**，但

1. 落一条 `artifact_bound_after_terminal` 事件；
2. 在 `model.TaskArtifact` 增字段并在 API 里暴露：

```go
	// Orphan marks a deliverable that arrived after its todo had already
	// reached a terminal state — visible so "failed todo with a done
	// deliverable" reads as a late arrival, not a contradiction.
	Orphan bool `json:"orphan,omitempty" bson:"orphan,omitempty"`
```

⚠️ 注意保留既有防重复的行为（2026-09-02 曾因重复上传把已完成剧本拒掉）：**同一 (todo, file name) 仍应折叠覆盖**，不要因为放开终态绑定而产生重复 artifact。

#### 步骤 3（可选，P2）：自动回补

`artifact_received` 时若 todo 为终态且距终态 **< 2h**，自动触发 reopen。开关 `AUTO_REOPEN_ON_LATE_ARTIFACT`（默认关闭）。

## 5. P-06 ｜ 输出位自动绑定 + 指纹去重 🟢 P2

### 根因

各步 agent 普遍「先传一次不带 `outputName`（触发『疑似最终交付物未绑定』提示），再补传一次带 `outputName`」→ 全流程任务里 **16 次上传 / 12 个绑定位**。

### 现状（已部分改善，勿重复）

`store_artifact.go:161` 的 `inferOutputBinding` **已经**实现了"单槽位 + mime 匹配 → 自动绑定"。

**但仍留下一个缺口**：`len(declared) > 1` 时**一律**返回 `unboundWarn=true`，即使已被绑定后只剩 **1 个未绑定槽**。P-06 要补的正是这个 case。

### 改动

#### 改动 1：单剩余槽位自动绑定

`inferOutputBinding` 签名需扩展（或改在更外层判断），把**已绑定槽位**纳入计算：

```go
// 当请求缺 outputName，而该 todo 声明的输出位「恰好只剩 1 个未绑定」时，
// 自动绑定并提示，而非强制重传。
// 注意：必须传入已绑定的 OutputName 集合，不能只看声明总数。
```

- 剩余未绑定数 **== 1** → 自动绑定（`boundBy = "inferred_single_left"`）。
- 剩余未绑定数 **> 1** → 维持现状：不猜绑，提示**列出候选槽位名**。

#### 改动 2：按指纹去重

现有去重（`store_artifact.go:278`）只按 `TransferID` 或 `(TodoID, FileName)`。

追加 **`(TaskID, FileName, FileSize, sha256)`** fingerprint 去重 —— 同一文件换个文件名重传也能被识别。

- `model.TaskArtifact` 需增字段（若无 sha256 来源，在上传落盘时计算）：

```go
	// SHA256 of the uploaded bytes; used together with (task, name, size) to
	// suppress duplicate artifacts of the same file under a new name.
	SHA256 string `json:"sha256,omitempty" bson:"sha256,omitempty"`
```

> ⚠️ 若上传链路（`internal/handler/agentfile*.go` / transfer 通道）当前不产出 sha256，**需先确认代价**再决定是否做本项；不要把这一项做成"改到一半"。可先只做改动 1。

### 验收标准

| #  | 断言                                                 |
| -- | -------------------------------------------------- |
| F1 | 单输出位步骤上传不带 `outputName` → **自动绑定成功**，不再出现「疑似未绑定」提示 |
| F2 | 多输出位且**剩余**未绑定数 > 1 → 维持现状（不猜绑），提示列出候选槽位           |
| F3 | 同一文件重复上传 → 第二条被去重，不新增 artifact                     |

**建议测试名**：`TestInferBindingWhenSingleSlotRemains` / `TestNoBindWhenMultipleSlotsRemain` / `TestArtifactFingerprintDedup`

## 6. P-08 ｜ run 预算耗尽可观测 + remind 退避 🟡 P1

### 现象（时间线）

| 时刻          | 事件                                                                    |
| ----------- | --------------------------------------------------------------------- |
| 22:57:26    | TD_05 收到 `todo.assigned`，启动 run_27e59…                                |
| 23:08:29    | 产物（打组表 + 提示词）**已上传**                                                  |
| 23:09:37    | `Turn ended with pending tool result ... budget=60/60`（**预算耗尽被静默截断**） |
| 23:09:46    | 平台重派，启动 run_67b7…                                                     |
| 23:17:58    | 重试 run 因 403 额度耗尽秒死                                                   |
| 23:48–06:54 | 平台**每 31 分钟** `todo.remind` 共 **13 次**                                |
| 06:56:21    | todo 才完成（**滞后 7h48m**）                                                |

### 根因

① 首轮 run **60 次工具调用预算耗尽**，在 `todo.complete` 发出前被截断；② 重试 run 因 LLM 额度耗尽秒死（节点侧 N-05 已修）；③ todo 未上报完成 → 平台 remind **无退避、无上限**，空转 8 小时。

### 现状（已确认未做）

`store/timeout_monitor.go`：

```go
	defaultTodoTimeout    = 30 * time.Minute
	defaultRemindInterval = 10 * time.Minute   // ← 固定间隔，无退避
	defaultMaxReminders   = 3
```

remind 路径为**固定 10 分钟间隔**；`todo.MaxRetries == 0` 时取 3 次封顶后判 failed。**无递增退避、无告警升级**（问题现象中的 31 分钟来自当时的实际配置，机制上同样是定频）。

> ✅ 已有可复用件：P-01 引入的 `internal/clawsynapse/client.go:370 publishBaseBackoff = 500ms` 与 `PublishWithRetry` 的指数退避写法（`398` 行），**退避实现风格照抄它**。


### 改动

#### 改动 1：remind 递增退避 + 上限 + 升级告警

引入按 `RemindCount` 递增的间隔，替代固定 `defaultRemindInterval`：

```
第 1 次: 15m
第 2 次: 30m
第 3 次: 1h
第 4 次: 2h（上限）
```

要点：

- 新增 `func remindBackoff(count int) time.Duration`，并在 `checkTodoTimeouts` 判定里用 `lastRemind.Add(remindBackoff(todo.RemindCount))` 替换现有 `lastRemind.Add(defaultRemindInterval)`。
- 因间隔递增，**总等待时长显著变长** → 必须与 P-03 硬闸协调：**硬闸仍是最终兜底**，不要因退避把 failed 判定的挂钟上限推得比 `hardDeadlineFor` 还晚（否则硬闸先杀，退避无意义）。
- 超过 N 次（建议 N = 3）后**升级为告警**：新增事件 `todo_remind_escalated`，在 `store_notification_internal.go` 加 `case`（照抄 `todo_dispatch_failed` 的写法，`category="todo"`, `priority="high"`），文案要点明「疑似 agent 静默卡死 / 预算耗尽，请人工介入」，并**不再继续无限 remind**。

#### 改动 2：run 预算耗尽的明确信号

平台侧能观测到的只是 gateway 返回的 run 终态文本（`Turn ended with pending tool result ... budget=60/60`）。

- 在平台解析 run 结果的路径上（`clawsynapse` 侧），**识别该形态**并落一条明确事件（如 `todo_run_budget_exhausted`），而非让它以普通"无进展"混过去。
- 与节点侧 **N-10**（技能侧「长步骤一次 run 只处理一组、先 `todo.complete` 再收尾」）配套。

> ⚠️ **不要**擅自提高工具的 run 预算上限——预算值在节点/hermes 侧，平台侧只做**识别 + 可观测**。若认为需要提高，先与节点侧确认。

### 验收标准

| #  | 断言                                    |
| -- | ------------------------------------- |
| H1 | 长任务在预算耗尽时，平台能给出**明确信号**（非静默截断）        |
| H2 | remind 间隔递增且有上限；超过 N 次触发告警事件          |
| H3 | 全流程重跑：`todo.remind` 次数 **≤ 3**（当前 13） |

**建议测试名**：`TestRemindBackoffSchedule` / `TestRemindEscalatesAfterMax` / `TestRunBudgetExhaustedEvent`

# T2.3b 实施规格：项目文件域（ProjectFile）→ Mongo 权威

> 状态：**规格已就绪，待用户在 A/C 之间拍板**（含一处用户可见的语义取舍）。
> 依据：`docs/t2.3-project-mongo-authority-plan-2026-09-15.md` §8.3 遗留项；复用 T2.1/T2.2/T2.3 已验证骨架。
> 编写：2026-09-15。

## 1. 目标

把项目文件域（`ProjectFile`：文件/文件夹元数据）的写路径从「**内存权威 + 尽力镜像（warn-only）**」改为「**Mongo 权威（write-through + Version 乐观锁）**」，兑现「重启零丢失」，使项目域**完整**达成 Mongo 权威（T2.3 只覆盖了 Project 聚合）。

## 2. 现状（代码事实）

| 事实 | 位置 | 问题 |
|------|------|------|
| `model.ProjectFile` **无 Version 字段** | `model/project_file.go:8-31` | 与 Project 同样需要新增 |
| `persistProjectFileUnsafe` = `ReplaceOne({_id}, pf, Upsert(true))` | `mongo_state.go:1783-1791` | **无 version filter** → 并发就地更新 last-writer-wins |
| **全部 9 处 persist 调用点都是 warn-only** | `SaveProjectFile:58`、`CreateMeetingMinutesFile:105`、`CreateFolder:161`、`RenameProjectFile:201`、`MoveProjectFile:257`、`saveProjectFileFromArtifactUnsafe:390/421/456`、`SetProjectFileLocalPath:1263` | 失败只 `s.log.Warn(...)` 后**照常返回成功** → 内存领先 Mongo，重启即丢（与 T2.1 会议域改造前的 bug 同源，但**更彻底**：连 rename/move 都吞错） |
| 删除是**完全 fire-and-forget** | `BatchDeleteProjectFiles:326`（`_ = s.deleteProjectFileUnsafe(id)`）、`DeleteProjectFile:593` | 删除失败被静默丢弃，Mongo 里留着「已删除」的行 → 重启后**文件复活** |
| 「幽灵」形态 | `SaveProjectFile:52-62`、`CreateMeetingMinutesFile:102-109`、`CreateFolder:161` | 先写 `s.projectFiles` + `projectFileIndex`（+ `transferFileIndex`）再 warn-only persist → 内存有、库里没有的记录 |
| 无 `VerifyProjectFileConsistency` / 无 backfill / 无 heal | — | 与 Project 聚合相比缺全套 |

**写点分类**：
- **新增（additive）**：`SaveProjectFile`、`CreateMeetingMinutesFile`、`CreateFolder`（+ `saveProjectFileFromArtifactUnsafe` 的新建分支）
- **就地更新（in-place）**：`RenameProjectFile`、`MoveProjectFile`、`SetProjectFileLocalPath`、`saveProjectFileFromArtifactUnsafe` 的**去重更新分支**（`snapshot` / `existing` 命中后改字段）
- **删除**：`BatchDeleteProjectFiles`、`DeleteProjectFile`（含 `deleteFolderChildrenUnsafe` 递归）

## 3. 🔴 关键结论：版本锁与 warn-only 不可混用（本批必须全量，不能只改一半）

直觉方案是「只把就地更新路径改成致命+版本锁，新增路径维持 warn-only」——**这个方案不成立**，必须放弃。原因：

- 同一文档会被两类路径写到：`saveProjectFileFromArtifactUnsafe` 的**去重分支**会更新既有文档，而 `RenameProjectFile` 也更新同一文档。
- 若保留任一**不带 version filter 的写**（warn-only 路径），它会用**内存里的（可能陈旧的）version** 整体覆盖 Mongo 文档 → 把 Mongo 的 version **改小或改回**，乐观锁当场失效。锁一旦被非锁路径写坏，后续用带 filter 的写就会**持续误判冲突**。
- 反之，若版本锁只作用于就地路径、而错误仍被 warn-only 吞掉，则「filter 未命中」的冲突**既不落库也不上报**，结果是**内存有改动、Mongo 无改动、调用方以为成功** —— 比现状（last-writer-wins，至少最后一笔落库）**更差**。

**结论：要么全量 Mongo 权威（A），要么维持现状并形式化接受（C）。没有可用的一半。**

## 4. 改造设计（选项 A）

### 4.1 骨架（与 T2.3 逐行同构，不再赘述细节）
- `model.ProjectFile` 增 `Version int json:"version" bson:"version"`（无 omitempty）。
- `mongo_state.go` 增 `projectFileVersionFloor = 1`、`projectFileVersionConflictCode = "PROJECT_FILE_VERSION_CONFLICT"`、`normalizeProjectFileVersion`、`applyProjectFileVersionedReplaceLocked`、`healZeroVersionProjectFileLocked`、`backfillProjectFileVersions`（于 `loadProjectFiles()` **之前**调用，`mongo_state.go:349`）。
- `persistProjectFileUnsafe` **改返回 `*transport.AppError`**；dup-key(E11000) 并入「未命中」分支。
- 🔴 **编译期护栏**（承 T2.3 §8.6 的教训）：`var _ func(*Store, *model.ProjectFile) *transport.AppError = (*Store).persistProjectFileUnsafe`
- `VerifyProjectFileConsistency` + `projectFileSnapshotMatches`：**只比** `ProjectID` / `ParentID` / `FileName` / `Version` / `IsFolder` / `len(children)`。
  - ⚠️ **不比** `LocalPath`（写成时序与字节落盘解耦，可能短暂空值）、**不比** `CreatedAt`（BSON 毫秒 vs Go 纳秒，同 T2.2/T2.3 的假 mismatch 坑）。
- `mutateProjectFileUnsafe` 快照回滚包装器（新增路径另按「建 → persist → 失败 `delete` + 回滚索引」处理，对齐 T2.3 的幽灵项目修法）。

### 4.2 写路径改造清单（含语义变更）

| 路径 | 现在 | 改为 |
|------|------|------|
| `SaveProjectFile` | warn-only | 失败 → 回滚 `projectFiles`/`projectFileIndex`/`transferFileIndex` 并**返错** |
| `CreateMeetingMinutesFile` | warn-only | 同上（⚠️ **调用方是 webhook**，见 §6） |
| `CreateFolder` | warn-only | 同上 |
| `RenameProjectFile` / `MoveProjectFile` | warn-only | `mutateProjectFileUnsafe`（零副作用回滚 + 冲突 409） |
| `SetProjectFileLocalPath` | warn-only | 致命 + 回滚（⚠️ 在字节已落盘之后调用，见 §6） |
| `saveProjectFileFromArtifactUnsafe` | warn-only（`:390` 刻意 warn-only 不回滚） | 致命；`:390` 的 warn-only 分支需**显式论证或一并致命**（⚠️ 调用方是 webhook 工件入库链） |
| `BatchDeleteProjectFiles` | `_ =` 忽略错误 | 逐条检查；失败计入既有 `Failed[]` 并**从内存恢复**该条（不得出现「内存删了、库里还在」） |
| `DeleteProjectFile` | `_ =` 忽略错误 | 致命 + 回滚（含 `deleteFolderChildrenUnsafe` 的递归删除） |

## 6. 风险（选项 A 的代价 —— 这是需要用户拍板的核心理由）

| 风险 | 说明 |
|------|------|
| **用户可见错误面** | 上传 / 建夹 / 改名 / 移动 / 删除从「Mongo 抖动也返回成功」变为「返回 5xx/409」。前端目前没有这些操作的重试 UI → 用户会看到失败提示 |
| **webhook 链路** | `CreateMeetingMinutesFile`、`saveProjectFileFromArtifactUnsafe` 由 webhook（会议纪要落盘 / agent 工件入库）调用；致命化后 Mongo 抖动会让 **webhook 回写失败**，进而可能触发上游重投（当前无幂等键，见 T2.6） |
| **`SetProjectFileLocalPath` 时序** | 它在字节已写入存储**之后**调用；此处返错会造成「字节已落盘、元数据未更新」的悬空，需要在实现时明确取舍（建议：保留 warn-only 但**明确注释**，因为它不参与用户可见的目录操作） |
| 批量删除的部分成功 | `BatchDeleteProjectFiles` 需保持「尽量删完」语义，不能因一条失败中断整批 |

## 8. 验收标准（选项 A）

1. **零副作用**：注入 persist 失败 → 接口返错且 `s.projectFiles` / `projectFileIndex` / `transferFileIndex` **全部**回到调用前快照（深拷贝逐字节相等）。
2. **无幽灵**：`SaveProjectFile` / `CreateFolder` / `CreateMeetingMinutesFile` 失败后内存中**不存在**该记录。
3. **乐观锁**：并发两次改名同一文件 → 第二次返回 `PROJECT_FILE_VERSION_CONFLICT`（409）。
4. **删除不复活**：删除成功后重启 rehydrate → 该行**不再出现**。
5. **重启零丢失**：上传 / 建夹 / 改名 / 移动后 rehydrate → 全部可读回。
6. **校验**：`VerifyProjectFileConsistency` 的 `mismatched == 0`（且确认不比 `LocalPath` / `CreatedAt`）。
7. **存量兼容**：无 version / 显式 0 的存量文档被 backfill 修复，不再永久锁死。
8. `gofmt -l` 归零 / `go build ./...` / `go test ./...` / `go test -race ./internal/store/...` / 活库整套 全绿；`store_project_test.go`、`project_file` 相关既有用例零回归。
9. 附带：T2.2 Task 域编译期护栏落地并通过反向验证（改签名 → 编译失败）。

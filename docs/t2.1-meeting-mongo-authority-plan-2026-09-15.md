# T2.1 实施规格：Meeting → Mongo 权威（阶段 2 第 1 批）

> 状态：**规格已就绪，待批准后实施**（架构级改动，遵循本项目「先方案后动手」）。
> 依据：`docs/optimization-plan-2026-09-11.md` §2.4 T2.1；依赖 T1.2（已完成）。
> 编写：2026-09-15

## 1. 目标

把会议域的写路径从「**内存权威 + 尽力镜像**」改为「**Mongo 权威**」：先 Mongo 提交并确认，再更新内存缓存；失败则**不产生内存副作用**。附带版本号 / 乐观锁防丢失更新。兑现「重启零丢失且可续开」。

## 2. 现状（代码事实）

`backend/internal/store/meeting.go` 的 `AddMeetingMessage`（L200-266）是当前典型形态：

| 行 | 行为 | 问题 |
|----|------|------|
| L210-218 | 生成 ID、**写入内存 map 与索引** | **内存先行** |
| L242 | `applyMeetingSessionFromMessageUnsafe` 把会话态镜到 meeting | 仅内存 |
| L244-258 | 会话态 `UpdateOne` 落库 | 失败**只 `s.log.Warn`（L255），不返错** → 静默丢 |
| L264-265 | 消息 `InsertOne` 落库 | 失败才返错，但**内存已改** → 内存领先 Mongo |

结论：Mongo 故障期间，内存里有、库里没有；重启即丢，且日志只有 warn。这正是阶段 2 要根治的。

同类写路径（需一并收口）：`CreateMeeting`(L20)、`UpdateMeetingStatus`(L139)、`UpdateMeetingSummary`(L365)、`UpdateMeetingMinutes`(L390)、L576 处 UpdateOne。

## 3. 改造设计

### 3.1 写路径顺序反转（核心）
对每一处会议写路径：
1. 在持锁内**先**执行 Mongo 写（`InsertOne` / `UpdateOne`）并 **检查 err**；
2. 失败 → 直接返回 `mongoWriteError(err)`，**不改动任何内存 map**；
3. 成功 → 再更新内存缓存。

> 关键约束：`*Unsafe` 函数只能在持锁内调用；Mongo 写放在持锁内会拉长临界区，需评估 `MONGO_TIMEOUT`(当前 5s) 对全局锁的影响 —— 这也是 T2.5（per-aggregate 细粒度锁）存在的理由，但**不在本批范围**。

### 3.2 会话态镜像失败改为致命
L244-258 的 `s.log.Warn` 分支改为：与消息写入合并为**同一次持久化**，或至少失败即返回错误，杜绝「静默丢会话态」。

### 3.3 版本号 / 乐观锁
- `model.Meeting` 增加 `Version int`（`json:"version" bson:"version"`）；`CreateMeeting` 置 1。
- 所有 `UpdateOne` 的 filter 带上预期版本：`bson.M{"_id": id, "version": cur}`，`$set` 中 `version: cur+1`。
- `ModifiedCount == 0` → 判定为版本冲突，返回 409 类错误（或按调用点重试一次），避免并发覆盖。

### 3.4 双写过渡与校验
- 过渡期保持「内存 + Mongo 双写」，加一个校验入口（对齐既有 `org_verify` / `backfillMeetingSessionUnsafe` 风格）：遍历对比内存与 Mongo 的会议记录，断言 `mismatched=0`。
- 启动时 `loadMeetings`（`mongo_state.go:1080`）继续负责 rehydrate，确保读回即可用。

## 5. 验收标准

1. **Mongo 失败零副作用**：注入 Mongo 写失败 → 接口返错，且内存 map **未**被修改（本批最重要的一条）。
2. **重启零丢失**：写入后模拟重启（rehydrate）→ 会议、消息、会话态（phase/target/turns/last_activity）全部可读回且能续开。
3. **乐观锁**：并发两次更新 → 第二次返回冲突而非静默覆盖。
4. **校验脚本**：双写过渡期 `mismatched=0`。
5. `go build ./...` + `go test ./...` + `go test -race ./internal/store/...` 全绿；既有 `meeting_rehydrate_test.go` 不回归。

## 6. 风险与回滚

| 风险 | 缓解 |
|------|------|
| 持锁内做 Mongo I/O 拉长临界区 | 本批先接受；T2.5 再拆细粒度锁。监控 `MONGO_TIMEOUT=5s` 下的写耗时 |
| 乐观锁引入新的冲突错误面 | 冲突仅在真实并发写出现；调用点需处理（重试或上抛） |
| 顺序反转改变既有行为 | 逐函数改 + 每处补测试；保留双写可回滚 |

**回滚**：改动按函数分批 commit，可整批 revert；双写期内内存仍可用。

## 7. 建议节奏

会议域写路径共 6 处（§2），建议按 `CreateMeeting → UpdateMeetingStatus → AddMeetingMessage → UpdateMeetingSummary → UpdateMeetingMinutes → L576` 逐个改，每改一个补一个「Mongo 失败零副作用」用例，最后统一加版本锁与校验脚本。

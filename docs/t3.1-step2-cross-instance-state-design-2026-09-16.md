## §0 结论先行（含对我上一轮判断的修正）

上一轮我说过：「读路径纯内存是 T3.1 的最大阻塞」。**这个判断被本轮调研部分推翻，需要修正**：

1. **写侧其实已经多实例安全了**（我上一轮低估了）。Task/Project/Meeting/ProjectFile 四个实体都已带
   `Version` 字段，任务域/项目域已有版本化 CAS 写入（`applyTaskVersionedReplaceLocked`），
   且 `mutateTaskUnsafe` 的「快照回滚」保证写冲突时内存零副作用。T2.6 的跨实例对抗探针
   （`t2.6_qa_xinstance_test.go`）已经证明：两个 Store 共享同一 Mongo 并发提升同一 todo，
   **恰好一个成功、另一个 409、库内不双派**。

2. **真正的硬阻塞是 SSE 跨实例不通**，而不是读陈旧。webhook 打到实例 B，
   但用户的 SSE 连接挂在实例 A → 事件永久丢失。这个「读回源 Mongo」**一点都解决不了**。
   而且前端已有轮询兜底（办公室 10s/30s、任务详情 10s），读侧陈旧对用户的可见影响是有界的。

因此本步的**优先级重排**为：

| 工作流 | 内容 | 阻塞程度 | 工作量 |
|---|---|---|---|
| **W1** | 写侧补全：409 冲突后主动回源刷新该实体 | 中（脏数据窗口无界） | **小** |
| **W2** | SSE 跨实例广播（事件总线） | **高（真·硬阻塞）** | 中 |
| **W3** | 读路径有界陈旧治理（按需回源） | 低（前端轮询已缓解） | 中，**可延后** |

**建议实施顺序：W1 → W2 → （验证双实例） → W3 按需**。

### 1.4 锁模型（W3 的关键约束）
- `store/store.go:20` 当前是**单把全局 `sync.RWMutex`**；`:21-38` 明确记录 T2.5 四域细粒度锁
  调用点已整体回退，`locks` 数组保留但**无任何生产调用点**，且规定「在此之前不得接入任何调用点」。
- `mongo_state.go:1601` 注释已承认：「Mongo 写在持锁内，会拉长临界区 —— 本批接受，留待 T05」。
- **推论**：若在持 `s.mu.RLock()` 期间做 Mongo **读**，会把「一次网络往返（`MONGO_TIMEOUT` 默认 5s）」
  塞进读临界区，串行化全站请求。这是 W3 最大的性能风险，也是我不推荐「每次 GET 都回源」的原因。

### 1.5 基础设施约束
- `docker-compose.yml:4-12`：Mongo 是 **standalone**（`command: ["--bind_ip_all"]`，无 `--replSet`）。
  → **Change Streams 不可用**，缓存失效不能靠 oplog 订阅。
- backend **不直连 NATS**：派发走 `HTTP POST /v1/publish → clawsynapsed → NATS`
  （`clawsynapse/client.go:338`）。go.mod 无 nats.go、无 redis 依赖。
- NATS 本身已在栈内（`clawsynapsed` 用），但**生产与本地共享同一 broker**（铁律：方案 A）。

## §2 问题定义（精确化）

不是「让读走 Mongo」，而是：

> **实例 A 的内存副本，如何在不把网络往返塞进全局读锁的前提下，避免长期陈旧？**

三种失效策略的本质差异：

| 策略 | 读开销 | 陈旧窗口 | 写开销 | 需要的基建 |
|---|---|---|---|---|
| (a) read-through 每次校验版本 | 每读 1 跳 Mongo（且持锁） | 0 | 无 | 无 |
| (b) 写冲突驱动刷新 | 0 | **无界**（A 不再写就一直脏） | 冲突时 +1 跳 | 无 |
| (c) 事件总线广播失效 | 0 | **有界**（落地为 ~500ms tailer 轮询） | 每次写 publish | Mongo outbox（NATS 版被否，见 §5） |

**我的推荐：(b) + (c) 组合，放弃 (a)。**
- (b) 单独用不够（§0 已述：409 只保护写，读侧脏窗口无界）——必须补「409 → 回源刷新该实体」。
- (c) 提供**主动失效**，把陈旧窗口压到亚秒级，且读路径零开销（不在锁内做 Mongo 读）。
- (a) 与 §1.4 的全局锁冲突最大，只在「单实体强一致读」的极少数场景（如 agent 节点回报前的
  归属校验）按需用 `GetTaskFromMongo` 显式走，不进主路径。

## §3 三个工作流的设计

### W1｜写侧补全：冲突后回源刷新（小，先做）

**问题**：A 写冲突 409 后回滚到**旧快照**，此后所有 GET 继续返回旧数据，直到 A 下次写再冲突。

**设计**：
1. 新增 `refreshTaskFromMongoLocked(taskID) *transport.AppError`：在**已持锁**前提下用
   `s.mongoContext()`（5s 有界）读 Mongo 最新文档，替换 `s.tasks[taskID]`，记 info 日志
   （`task_refreshed_after_version_conflict`，带本地/远端 version）。
2. 在 `mutateTaskUnsafe` 的 persist 失败分支中，**仅当**错误码是 `TASK_VERSION_CONFLICT`
   时调用它（快照回滚之后）。`mongoWriteError`（500，Mongo 真挂了）**不刷新**——
   此时读 Mongo 大概率也失败，且语义不同。
3. 冲突**不自动重试**（保持现状返回 409 给调用方）。理由：自动重试会把「并发写」变成
   「静默覆盖」，正是乐观锁要消灭的（见 `healZeroVersionTaskLocked` 注释）。
   重试策略交给上层：agent 回报路径由 webhook handler 决定，用户操作路径由前端提示。
4. 项目域/会议域同款（`mutateProjectUnsafe` 已对齐任务域，同改动）。

**为什么安全**：改动全部在「已经要返回错误」的分支里，成功路径逐字节不变。

**验收**：
- 单测（fake seam，无需 Mongo）：冲突 → 内存被替换为远端版本、version 与远端一致。
- 单测：`mongoWriteError` 分支**不**触发刷新。
- 扩展现有 `t2.6_qa_xinstance_test.go`：双实例冲突后，输家的后续 `GetTask` 返回**赢家写入的值**
  （这条现在必挂，是 W1 的核心回归）。

### W2｜SSE 跨实例广播（中，真阻塞）——**最终落地：Mongo outbox + tailer**

**问题**：`publishUserEventUnsafe` 只推本进程 channel。

**原推荐方案（NATS fan-out）已被甲方否决**（决策点 1：不接受 backend 直连 NATS）。
**实际落地设计（`sse_bus.go`）**：
1. 写侧咽喉点 `publishUserEventUnsafe` 保持本地直投**不变**（零延迟），额外把事件
   **非阻塞**塞进进程内 outbox channel（缓冲 256；满则丢弃并计数，绝不阻塞业务写）。
2. 独立 writer goroutine：`user_events_seq` 单文档 `$inc` 分配全局单调 seq →
   以 `_id=seq` 写入 `user_events`（载荷存 **JSON 字符串**——BSON 往返会把
   `model.Event` 的 `json:"id"` 键退成 `_id`，断裂前端解析）。
3. 每实例 tailer goroutine：500ms 轮询 `{_id: {$gt: cursor}}`，seq 空洞等 3 轮再跳过
   （容忍 writer 分配 seq 后崩溃）；按 `origin_id` 跳过自己发的 → `deliverUserEvent`
   投给本进程订阅者。游标启动时对齐到 max seq（不回灌历史）。
4. **降级不变量**：`SSE_BROADCAST_ENABLED=false`（默认）→ `outboxCh==nil`，enqueue 直接
   返回 false，行为与现状**逐字节一致**；Mongo 写失败只计数降级为「仅本地投递」。
5. outbox 集合靠 `created_at` TTL 索引（60s）自动清理，不无限增长。

**被否决的备选**（留档）：
- **W2-alt 粘性路由（sticky session）**：webhook 入口是 clawsynapse 回调、**不带 userID**，
  仍需先查 task→owner 才能路由，实际做不到纯 LB 解决 → 不可行。
- **W2-alt2 轮询兜底**：实时性从 ms 退化到 10s，办公室体验明显变差 → 仅作最终退路。

### W3｜读路径有界陈旧（中，可延后）

**设计（若 W2 落地后仍需更强读一致性）**：
- 不做「每次 GET 回源」（§1.4 锁风险）。
- 改为**TTL 惰性刷新**：内存对象记录 `loadedAt`，GET 时若 `now-loadedAt > readTTL`（建议 3~5s）
  且**非 leader 刚写过**，则**释放读锁后**异步回源、下次读生效（stale-while-revalidate）。
  → 关键：Mongo 读**绝不**在持 `s.mu` 时发起。
- 前置依赖：**T05 原子性整批迁移细粒度锁**（`store.go:29-30` 已为此预留 `locks` 数组）。
  在全局单锁下做 W3 风险过高。

**结论：W3 应排在 T05 之后，不在本轮。** 当前由 W1+W2+前端轮询覆盖，用户可见陈旧 ≤10s。

## §5 决策点（2026-09-16 甲方已拍板）

1. **W2 是否允许 backend 直连 NATS？** → **不接受**。
   落地改为 **Mongo outbox + tailer**（`sse_bus.go`）：写侧咽喉点非阻塞入队 →
   单文档 `$inc` 分配全局 seq → `user_events` 集合（`_id=seq`）→ 各实例 tailer 500ms
   轮询拉取、按 `origin_id` 跳过自己发的。跨实例延迟 ~500ms（远优于退化的 10s 轮询），
   零新增外部依赖。outbox 写失败只计数降级，绝不影响业务写路径。

2. **可接受的读侧陈旧窗口？** → **≤10s 可接受**。
   W3（读侧 TTL 刷新）**本轮不做**，留给 T05 细粒度锁之后；前端轮询兜底已覆盖。

3. **409 冲突后是否自动重试一次？** → **不重试**。
   W1 只回源刷新内存（消除「输家永久吐旧数据」的无界脏窗口），409 语义原样上交调用方。

4. **本轮做到哪？** → **选项 B：W1 + W2 全做**。
   已交付：`refresh_on_conflict.go`（task/project/projectFile 三域回源刷新）、
   `sse_bus.go`（outbox+tailer）、`t31_step2_integration_test.go`（真 Mongo 双实例 7 用例）、
   `sse_bus_test.go`（纯内存 8 用例）。两开关默认 false，关闭态行为与改造前逐字节一致。
   集成测试还暴露并修复了一个真库才可见的 bug：Go 驱动把 `FindOneAndUpdate(upsert)`
   插入成功返回的 `value:null` 报成 `ErrNoDocuments`，被 leader CAS 的 fail-safe 误判为
   错误 → 首次获取租约必失败。已在 `mongoLeaderCAS.tryAcquireOrRenew` 显式视为「抢到」。

# 环境使用守则：本地开发 / 生产运行（方案 A）

> 定于 2026-09-11。核心约定：**生产 = 唯一活动环境，本地 = 纯粹的开发环境。**

---

## 一、为什么要这条守则

本地与生产**共用同一个 NATS broker**（`nats://175.27.135.91:4222`），
两侧 clawsynapse 都能发现并记录**同一批 Hermes 节点**（7 个，`node_id` 完全相同）。

```
本地 backend ──> 本地 clawsynapse (n1-cb979d6a) ──┐
                                                  ├──> 共享 NATS ──> 7 个 Hermes 节点
生产 backend ──> 生产 clawsynapse (n1-7d931c27) ──┘     175.27.135.91:4222
```

**后果**：若两侧同时向同一 `node_id` 发消息 → 节点收到**重复指令**（同一份剧本写两遍／同一批资产出两遍图）。

---

## 二、铁律

### ✅ 允许

| 操作 | 说明 |
|---|---|
| 改前端源码 + `npm run dev` 看 UI | 不触发任何 agent 消息 |
| 改后端源码 + 容器内 `go build ./...` 编译检查 | 纯编译，不派发 |
| 本地 MongoDB 结构探索 / 写只读查询 | 不碰节点 |
| 本地起 backend **但不开任务** | 节点发现是幂等的，不会自动派活 |
| 前端连生产后端调试（桌面端「服务器设置」指向生产） | 读生产数据，不影响节点 |

### 🔴 禁止

| 操作 | 原因 | 后果 |
|---|---|---|
| **本地创建任务 / 启动 todo 流水线** | 本地 clawsynapse 会向真实节点发 `todo.assigned` | 与生产抢指令 → 节点收到重复任务 |
| **本地点「开始执行」/ 触发 PM 规划** | 同上，会推 `task.message` | `NudgePlanningPM` 会让节点开始干活 |
| **本地恢复/重跑历史任务** | 即便任务「是历史数据」，重启也会派发 | 意外唤醒真实节点 |
| **本地 approvals / 催办 / 重派发** | `dispatchNextTodo` 会发消息 | 同上 |

## 三、需要本地连节点时（例外流程）

如果确实要在本地做**端到端联调**，按这个顺序做：

```
1. 先在生产停掉所有活动任务（确认无 in_progress）
2. 本地临时起 backend + clawsynapse
3. 做完验证后，立即停掉本地 backend
4. 记录：这段时间生产不要发起任务
```

⚠️ 这是**互斥窗口**，不是并行方案。要真正并行，必须做「本地独立 NATS」（方案 B）。

## 四、随时自检的命令

### 4.1 检查本地是否在发消息（应为 0）

```bash
docker logs trustmesh-clawsynapse --since 30m 2>&1 | grep -cE "message published|message.sent"
```

### 4.2 检查本地是否有可派发的任务

```bash
docker exec mongo mongosh trustmesh --quiet --eval \
  'print("todos: "+db.todos.countDocuments({status:{$in:["pending","in_progress"]}})); db.tasks.find({status:{$in:["pending","in_progress"]}},{title:1,agent_id:1}).forEach(function(t){print(t._id+" | "+t.title+" | agent="+t.agent_id)});'
```

**判定**：若 `agent_id` 全是 `undefined` → 不会派发（安全）。
若有 `agent_id` 有值 + todo 处于 pending → **立刻停本地 backend**。

### 4.3 检查本地 backend 是否在派发

```bash
docker logs trustmesh-backend --since 30m 2>&1 | grep -icE "nudge|dispatch|todo_assigned"
```

### 4.4 检查生产当前是否在跑任务（发起本地测试前必查）

```bash
ssh -i "D:/AIWorkspace/公司/vic_key.pem" -p 62000 cloudUser@175.27.135.91 \
  "docker exec trustmesh-mongo mongosh trustmesh --quiet --eval 'print(\"prod todos: \"+db.todos.countDocuments({status:{\$in:[\"pending\",\"in_progress\"]}}))'"
```

## 五、一键「本地静默」开关（推荐常备）

不想每次手动检查？直接把本地 clawsynapse 停掉，本地就**物理上无法**向节点发消息：

```bash
# 静默本地（最安全）
docker stop trustmesh-clawsynapse

# 需要联调时再启
docker start trustmesh-clawsynapse
```

**代价**：本地 agents 列表会全部变 `offline`（因为不再同步节点心跳）。
**收益**：本地**不可能**误伤生产。

> 建议：**日常保持 stop**，只在明确要做端到端联调时 start。

## 六、生产侧的已知噪声（A 方案下可忽略）

生产日志每 10 秒刷一条 warn：

```
{"caller":"clawsynapse/trust_sync.go:122","msg":"failed to create join request",
 "from":"n1-3945d737bee9026f8e8860b974e84de5","error":"node_id already registered as an agent"}
```

**原因**：node `n1-3945d737…`（=「编剧」agent）已在 `agents` 表注册，
clawsynapse 的 trust_sync 仍在尝试为它创建 join request，被业务侧正确拒绝。

**影响**：无功能影响，仅日志噪声（~6 条/分钟）。
**要不要修**：可选。修法是让 `trust_sync` 在遇到 `node_id already registered` 时直接跳过，
不再重试 —— 属 clawsynapse 侧改动，需要重建镜像。

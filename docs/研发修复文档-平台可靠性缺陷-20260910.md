## P-01 ｜ 顺序自动派发失败被静默吞掉 🔴 P0

### 根因

`WebhookHandler.dispatchNextTodo`（`internal/clawsynapse/webhook.go:1789-1826`）有 **4 条 `return task` 静默路径**：

```go
func (h *WebhookHandler) dispatchNextTodo(ctx context.Context, task *model.TaskDetail) *model.TaskDetail {
	if h == nil || task == nil || h.client == nil {
		return task                                    // ← ① NATS/client 未就绪
	}
	todo := task.NextDispatchableTodo()
	if todo == nil { return task }
	if appErr := h.store.CheckTaskProjectActive(task.ID); appErr != nil {
		h.log.Warn("skip sequential todo dispatch for archived task project", ...)
		return task                                    // ← ② 项目归档
	}
	payload := h.buildTodoAssignedPayload(task, todo)
	if _, err := h.client.Publish(ctx, todo.Assignee.NodeID, "todo.assigned", payload, task.ID, nil); err != nil {
		h.log.Warn("sequential todo dispatch failed", ...)   // ← ③ 发布失败（本次真凶）
		return task
	}
	updatedTask, appErr := h.store.RecordSequentialTodoDispatch(task.ID, todo.ID)
	if appErr != nil {
		h.log.Warn("failed to persist sequential todo dispatch", ...)
		return task                                    // ← ④ 落库失败
	}
	return updatedTask
}
```

四条路径全部：**不重试、不落事件、不改状态、不通知用户**。
`Client.Publish`（`internal/clawsynapse/client.go:316`）全文无 `retry`/`backoff`。

### 目标行为

1. 瞬时故障自动重试（有上限）。
2. 仍失败 → 落 `todo_dispatch_failed` 事件 + 用户通知（界面可见）。
3. **新增自愈兜底**：即使所有补救都失败，也有后台对账把断掉的链重新接上（覆盖进程重启、网络分区等所有静默失败模式）。

> 💡 **设计要点**：只加重试只能覆盖「网络抖动」这一种。真正的保险是**幂等自愈对账**——它不关心失败原因，只看「该派发的没派发」。两者都做。

#### 步骤 2：`store/workflow.go` — `RecordSequentialTodoDispatch` 记录派发结果

该函数在 `internal/store/workflow.go:163-218`。在 `recordTodoDispatchUnsafe` 之后补写字段。
新增一个供失败路径调用的方法（**必须持锁**，注意 `*Unsafe` 约定）：

```go
// RecordSequentialDispatchFailure records a failed sequential dispatch so the
// pipeline stall becomes observable and the reconciler can retry later.
func (s *Store) RecordSequentialDispatchFailure(taskID, todoID, errMsg string) *transport.AppError {
	s.mu.Lock()
	defer s.mu.Unlock()

	task, ok := s.tasks[taskID]
	if !ok {
		return transport.NotFound("task not found")
	}
	idx := findTodoIndex(task, todoID)
	if idx < 0 {
		return transport.NotFound("todo not found")
	}
	todo := &task.Todos[idx]
	now := time.Now().UTC()
	todo.DispatchAttempts++
	todo.LastDispatchAt = &now
	msg := errMsg
	todo.LastDispatchErr = &msg

	content := fmt.Sprintf("自动派发失败：%s（第 %d 次，将由后台对账自动重试）", todo.Title, todo.DispatchAttempts)
	s.addEventUnsafe(task.UserID, task.ProjectID, task.ID, todo.ID,
		"system", "dispatcher", "派发器", "todo_dispatch_failed", &content,
		map[string]any{
			"todo_id":       todo.ID,
			"todo_title":    todo.Title,
			"attempts":      todo.DispatchAttempts,
			"error":         errMsg,
			"assignee_name": todo.Assignee.Name,
		}, now)
	if err := s.persistTaskBundleUnsafe(task.ID); err != nil {
		return mongoWriteError(err)
	}
	s.publishTaskUnsafe(task.ID)
	return nil
}
```

> ⚠️ **持锁校验**：`addEventUnsafe` / `persistTaskBundleUnsafe` 都是 `*Unsafe`，只能在持锁状态下调用。上面已 `s.mu.Lock()`，正确。

#### 步骤 4：`clawsynapse/client.go` — `Publish` 加重试

在 `Publish`（L316）外层包一个重试。**只在传输层错误时重试**（请求没到节点，无重复投递风险）；节点返回的 4xx 不重试。

```go
// publishRetryConfig controls transient-failure retries for outbound delivery.
// Only transport-level errors are retried: a request that never reached the
// node cannot have been delivered, so retrying is safe. Node-side 4xx are
// never retried (the node explicitly rejected them).
const (
	publishMaxAttempts = 3
	publishBaseBackoff = 500 * time.Millisecond
)

// PublishWithRetry publishes with bounded exponential backoff on transport
// errors. Kept separate from Publish so callers that must not retry (e.g.
// fire-and-forget notifications) keep the original semantics.
func (c *Client) PublishWithRetry(ctx context.Context, targetNode, msgType string, payload any, sessionKey string, metadata map[string]any) (*PublishResult, error) {
	var lastErr error
	for attempt := 1; attempt <= publishMaxAttempts; attempt++ {
		res, err := c.Publish(ctx, targetNode, msgType, payload, sessionKey, metadata)
		if err == nil {
			return res, nil
		}
		lastErr = err
		// 仅重试传输层错误（连接拒绝 / 超时 / TLS 握手）
		if !isTransportError(err) {
			return nil, err
		}
		if attempt == publishMaxAttempts {
			break
		}
		select {
		case <-ctx.Done():
			return nil, ctx.Err()
		case <-time.After(publishBaseBackoff * time.Duration(1<<(attempt-1))):
		}
	}
	return nil, lastErr
}

func isTransportError(err error) bool {
	if err == nil {
		return false
	}
	// 复用现有判定：net.Error / url.Error / context 超时均视为传输层
	var netErr net.Error
	if errors.As(err, &netErr) {
		return true
	}
	var urlErr *url.Error
	if errors.As(err, &urlErr) {
		return true
	}
	return errors.Is(err, context.DeadlineExceeded)
}
```

> 需在文件顶部 `import` 补 `"errors"`、`"net"`、`"net/url"`（若尚未引入）。

#### 步骤 6（关键）：新增自愈对账 reconciler

```go
package store

// StartDispatchReconciler periodically re-dispatches todos that should have
// been dispatched but were not. It is the safety net for every silent failure
// mode in dispatchNextTodo (transient publish errors, process restarts,
// network partitions): instead of enumerating causes, it simply asks
// "is there a dispatchable todo that never got dispatched?" and retries.
//
// Idempotency: RecordSequentialTodoDispatch rejects non-pending todos
// (TODO_NOT_PENDING), and the webhook already de-dupes inbound messages via
// processedMessageKey, so a duplicate attempt is a no-op.
func (s *Store) StartDispatchReconciler(ctx context.Context, interval time.Duration, dispatch func(taskID, todoID string) error, log *zap.Logger) {
	if interval <= 0 {
		interval = 2 * time.Minute
	}
	ticker := time.NewTicker(interval)
	defer ticker.Stop()
	for {
		select {
		case <-ctx.Done():
			return
		case <-ticker.C:
			s.reconcilePendingDispatches(dispatch, log)
		}
	}
}

func (s *Store) reconcilePendingDispatches(dispatch func(taskID, todoID string) error, log *zap.Logger) {
	s.mu.RLock()
	type candidate struct{ taskID, todoID string }
	var cands []candidate
	for _, task := range s.tasks {
		if task.Status != "in_progress" {
			continue
		}
		todo := task.NextDispatchableTodo()
		if todo == nil || todo.Status != "pending" {
			continue
		}
		// 只重试「停滞超过 3 分钟」的，避免与正常派发抢跑
		if todo.LastDispatchAt != nil && time.Since(*todo.LastDispatchAt) < 3*time.Minute {
			continue
		}
		cands = append(cands, candidate{task.ID, todo.ID})
	}
	s.mu.RUnlock()

	for _, c := range cands {
		if err := dispatch(c.taskID, c.todoID); err != nil && log != nil {
			log.Warn("dispatch reconcile failed", zap.String("task_id", c.taskID), zap.String("todo_id", c.todoID), zap.Error(err))
		} else if log != nil {
			log.Info("dispatch reconcile succeeded", zap.String("task_id", c.taskID), zap.String("todo_id", c.todoID))
		}
	}
}
```

### 根因（修正版）

问题不是「评论不该续命」，而是**没有区分「进展型评论」与「故障型评论」**。
崩溃中的 agent 每 30 分钟上报一次 `⚠️【执行侧故障上报】hermes run failed`，这类纯噪声被当成有效活动，于是：

```
提醒 → agent 报错 → 评论续命 → 计时归零 → 再提醒 → 无限循环
```

证据：18 次提醒**全部 `remind_count=1`**；全库 115 条提醒中 103 条（89.6%）为 1。

### 目标行为

- **进展型评论**（persona 汇报进度、交付说明等）→ 照旧续命（保住现有能力）。
- **故障型评论**（明确匹配错误特征）→ **完全不续命**：不更新 `LastActivityAt`、不重置 `RemindCount`。
- 无法归类的模糊评论 → **按续命处理**（保守，宁可误放过不可误杀）。

## P-07 ｜ LLM 凭证池与错误分类 🟡→🔴 P0（v2 新增）

### 现象

**证据 A — 403 额度耗尽（分镜师 @103）**
```
15:17:56 credential pool: marking model_config exhausted (status=403), rotating
15:17:56 credential pool: no available entries (all exhausted or empty)
15:17:56 HTTP 403: chat pre-consumed quota failed, user quota: $0.034762, need quota: $0.084910
15:17:58 Non-retryable client error: 403 ... 'local:insufficient_quota'
```
→ 凭证池**无任何可用条目**，重试 run 秒死。

**证据 B — 400 代理 120s 超时（执行总控，13:56–14:06）**
```
HTTP 400: The origin web server did not return a complete response within the
120-second Proxy Read Timeout window ... (base_url=https://api.openlux.ai/v1)
```
→ 直接对应 **③→④ 的 56 分钟派发空档**。

**证据 C — 402 余额不足（导演 @3 / 执行总控）**
```
402 - {'error': {'message': 'Insufficient Balance'}}
Auxiliary: marking openrouter unhealthy for 60s (payment / credit error)
```
→ 辅助模型在 openrouter / nous / deepseek 间反复降级，**标题生成全部失败**。

### 改动

1. **凭证池**：为每个工位配置 **≥2 条有效凭证**（现池为空 → 403 秒死）；`exhausted` 标记必须**可恢复**（TTL 或主动探测），不能一次 403 就永久出局。
2. **错误分类策略**：

   | 错误 | 处置 |
   |---|---|
   | `402` / `403 (quota/balance/credits)` | 标记该凭证 exhausted → **轮换下一条**；**仅当池内无可用条目**才向上抛（由节点侧 **N-05** 熔断） |
   | `400 Proxy Read Timeout (120s)` | **可重试**（指数退避 5s / 15s / 45s），**不要**归入不可重试 |
   | 其它 4xx | 不重试 |

3. **额度水位监控 + 告警**：低于阈值（剩余 quota < 单次预估 2 倍）提前告警。
4. **辅助模型降级链兜底**：避免 openrouter / nous / deepseek 同时不可用导致标题生成全挂（可设本地兜底或跳过）。

### 🔴 与节点侧 N-05 的分层契约（冲突 C1 的仲裁）

```
403 + quota
  ├─ 池还有可用凭证 → 轮换下一条                 ← 本节 P-07（平台）
  └─ 池已空         → 熔断：停止重试 + 明确上报   ← 节点侧 N-05
```
> **两端必须同批上线**：一边轮换一边熔断会互相抵消。

### 验收标准

| # | 断言 |
|---|---|
| G1 | 模拟单凭证 403 → **自动切下一凭证并成功**，不秒死 |
| G2 | 模拟 400 120s 超时 → 退避重试后成功 |
| G3 | 池内全部凭证 403 → 精确向上抛「额度耗尽」，节点侧收到明确原因 |
| G4 | `Title generation failed` 不再出现 |

# T2.5 backend store 细粒度锁 —— 独立对抗验证报告（QA）

> ## ⛔ 本报告已作废（2026-09-16）
>
> **本报告的结论（尤其是「AC-1 PASS」「未发现源码缺陷」）已全部失效，请勿据此做任何决策。**
> 原文保留在下方仅作历史留档与追责线索，**不代表当前代码状态**。
>
> **作废原因概要**（由第二轮独立对抗验证逐条证伪，共 6 处）：
>
> 1. **AC-1「PASS」为假**：报告只测了 `lockProject()` 等**锁 helper 原语**，从未测真实公开 API。
>    实测独占 `s.mu` 后调用四域 19 个真实 API，**19/19 全部阻塞** ⇒ 细粒度锁未生效。
> 2. **AC-4 自承活库未跑**：`*_mongo_authority_test.go` 的活库分支未执行即判 PASS。
> 3. **AC-6 扫描口径错误**：运行期护栏只插桩 `lockAggregates` / `coarseWithAggregates`，
>    对 store 包内 40+ 处裸 `s.mu.Lock()/RLock()` 完全不可见（假阴性）；持锁栈为包级全局
>    而非 goroutine 局部（假阳性）。
> 4. **结论「未发现源码缺陷」被 P0 证伪**：存在 **4 处 P0 数据竞争** —— T2.5 只迁了四域，
>    store 包内仍有 44 个函数 / 11 个文件只持 `s.mu` 读写同一批 map，导致同一张 map 出现
>    `s.mu` 与聚合锁**两把互不互斥的锁**，互斥失效。`-race` 已复现 `WARNING: DATA RACE`，
>    生产可达路径可致 `fatal error: concurrent map read and map write`（进程崩溃）。
> 5. **AC-1 零收益被掩盖**：50 个迁移点里 46 个走 `coarseWithAggregates`(= 仍先取全局 `s.mu`)，
>    真正纯聚合锁仅 4 处，改造几乎没有带来并发度收益。
> 6. **读并发回退（P1）**：22 处 `s.mu.RLock()` 被改成独占锁。
>
> **后续处置：主理人已拍板「方案 A —— 回退 T2.5 的调用点改动，保留锁基础设施」。**
> `store` 包运行时行为已回退至与基线 `4bcff06` 完全一致（同一张 map 仍只有 `s.mu` 一把保护锁），
> `Store.locks` 与 `store_lock.go` 的原语保留，供后续 T05 做**原子性整批迁移**时复用。
>
> **决策与完整复盘见：`docs/t2.5-rollback-decision-2026-09-16.md`**

## 2. 两处必修缺陷复核

### 缺陷 #1（编译失败 + 内层锁永久泄漏）—— 已修复
`CancelTask` 改用 `release := s.coarseWithAggregates(AggProject, AggTask)` 后，原 7 处 return 仍直接 `s.mu.Unlock()`，`release()` 从未调用 → 编译失败 + 内层 `AggProject`/`AggTask` 永不释放。

逐行核对 `788fcfc`：7 处（task not found / ensureTaskProjectActiveUnsafe 失败 / 已取消 / 已终态 / mutateTaskUnsafe 失败 / persistAgentGraphUnsafe 失败 / 正常收尾）**全部改为 `release()`**，无残留 `s.mu.Unlock()`。

### 缺陷 #2（伪造审批）—— 已修正
`store.go` 注释现明确写为：「mu 保留为 sync.RWMutex 系对设计契约（§1 Q2 要求降级为 sync.Mutex）的**偏离**。理由：保留 sync.RWMutex 是 sync.Mutex 的严格超集，可避免改动数十处既有 `s.mu.RLock()` 调用点，优先保障 AC-4（T2.x 语义 100% 不变）。**主理人已于 2026-09-15 复核并同意此偏离**；mu 的 Mutex 降级留作 P2 项。」无未经证实的审批声称。

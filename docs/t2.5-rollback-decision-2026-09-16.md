## 一、为什么回退

### 1.1 P0：半迁移破坏互斥，产生真实数据竞争（4 处）

T2.5 把 Project / ProjectFile / Task / Meeting 四域的写路径迁到 per-aggregate 聚合锁，但 store 包内**仍有一批函数只持全局 `s.mu`** 读写同一批 map。于是同一张 map 出现两把**互不互斥**的锁，互斥保护失效。

| 纯聚合锁点（读方） | 读的 map | 仍只持 `s.mu` 的写方（证据链） |
|---|---|---|
| `store_project.go` `CheckTaskProjectActive` | `s.tasks` | `workflow.go` `UpdateTodo` / `AddTaskComment` / `AppendTodo` / `ReviewTodo`、`timeout_monitor.go` `SetTodoAssignedAt` / `checkPlanningTimeouts`、`store_planning.go` 多处（共 44 个 / 11 文件） |
| `store_project_file.go` `GetProjectFileByID` | `s.projectFiles` | `store_artifact.go:203 SaveArtifactWithFiling`（**仅 `s.mu`**）→ `saveProjectFileFromArtifactUnsafe` |
| `store_project_file.go` `GetProjectFileByTransferID` | `s.projectFiles` + `s.transferFileIndex` | 同上（该 Unsafe 函数同时写这两张 map） |
| `meeting.go` `GenerateMeetingMinutesFile` 内联段 | `s.projects` | `store_workflow_template.go:303/383/475`（**仅 `s.mu`**）→ `mutateProjectUnsafe`；触发面窄（仅失败回滚分支） |

- `-race` **实测复现** `WARNING: DATA RACE`（`CheckTaskProjectActive` 读 vs `s.mu`-only 写路径 `mapassign_faststr`）。
- **生产可达**：`CheckTaskProjectActive` 由 `handler/task.go:279`（HTTP）与 `clawsynapse/webhook.go:2155/2312`（agent webhook 热路径）调用；写路径由 timeout_monitor 定时器与 HTTP 写接口并发触发 ⇒ 可致 **`fatal error: concurrent map read and map write`（进程崩溃）**。
- 诚实标注：**只有 `s.tasks` 一处做了 `-race` 运行时复现**，其余 3 处为静态调用链判定（写者与读者分属两把不互斥的锁是可从代码直接判定的结构性事实，但未逐个跑出 race 日志）。

### 1.2 AC-1 完全没达成：零并发收益

- 50 个迁移点中 **46 个走 `coarseWithAggregates`（= 仍先取全局 `s.mu`）**，真正纯聚合锁仅上述 4 处。
- QA 独占 `s.mu` 后测**真实公开 API**：`GetProject` / `ListProjects` / `GetTask` / `ListTasks` / `GetMeeting` / `ListMeetings` / `GetProjectFile` / `ListProjectFiles` / `CancelTask` … **19/19 全部阻塞**；对照组 3 个纯聚合路径不阻塞（证明测量有效、非恒绿穿透）。

### 1.3 P1：读并发回退

22 处 `s.mu.RLock()`（共享读）被改为独占锁（`GetTask` / `ListTasks` / `GetMeeting` / `ListMeetings` / `GetProjectFile` / `ListProjectFiles` / `BrowseProjectFiles` …）。本该提升并发的重构，**实际降低了读并发度**。

### 1.4 全量迁移的代价（选择不做的那条路）

| 项 | 规模 |
|---|---|
| 需迁移的函数 | **44 个 / 11 个文件**（workflow.go 18、store_planning.go 7、store_artifact.go 4、store_workflow_template.go 4、timeout_monitor.go 4、store_org.go 2、其余 5 文件各 1） |
| 需重订契约的 Unsafe 裸函数 | **8 个**（自身不取锁，写哪张 map 取决于调用方，是半迁移最容易漏的地方）：`store.go:529 mutateTaskUnsafe`、`:560 mutateProjectUnsafe`、`:592 mutateProjectFileUnsafe`、`store_events.go:93 addEventUnsafe`、`store_project_file.go:199 rollbackProjectFileAddUnsafe`、`:456 saveProjectFileFromArtifactUnsafe`、`:719 deleteFolderChildrenUnsafe`、`workflow.go:1521 addCommentUnsafe` |

## 二、根因（结构性，务必记住）

> **同一张 map 的守护锁只能有一把 ⇒ 细粒度锁不能增量迁移 map 的访问者集合。**

只要还有 1 个函数留在 `s.mu`，这张 map 就有两套锁、互斥即失效。已迁移 4 域 = 14 张 map，因此 T2.5 原 scoping（只迁四域、把 44 个函数留到 T05）**结构上不可能满足 AC-1**。

这也解释了为什么 46/50 迁移点被迫用 `coarseWithAggregates`：实现时大概已撞到这个矛盾，于是选择「既取 `s.mu` 又取聚合锁」来同时兼容两边 —— 代价是 AC-1 完全失效。

**推论（方法论教训）**：
1. **评估锁重构必须测真实公开 API，不能只测 helper。** 第一版报告判 AC-1 PASS，是因为用例只直调 `s.lockProject()` / `s.lockTask()` —— 即便 100% 生产路径仍用全局锁，它也会恒绿。典型的「测了锁原语、没测迁移效果」。
2. **`-race` 必须带活库跑。** `*_mongo_authority_test.go` 的活库分支由 `TRUSTMESH_TEST_MONGO_URI` 门控，未设置则 `t.Skip`。只跑无 Mongo 的 `-race` 不构成 AC-4 验证。
3. **护栏要证明有鉴别力。** 反向验证（故意破坏实现 → 相关用例必须变红）不可省；恒绿的护栏等于没有护栏。

## 五、后续：若重启细粒度锁（T05）的前置条件

1. **必须原子性整批迁移**：一次 commit 内把 44 个函数 + 8 个 Unsafe 裸函数契约全部迁完，不留中间态。**禁止再分阶段迁移**。
2. **聚合锁上 RWMutex**：恢复并提升读并发（本次 22 处退化为独占锁的教训）。
3. **收窄聚合集合**：按调用点真实触及的 map 逐个核对，避免「会议 CRUD 一律取 `AggMeeting+AggProject`」这类过宽集合。
4. **反向嵌套护栏改 goroutine 局部**：现有 `lockHeldStack` 是包级全局切片（假阳性），且只插桩 helper、对裸 `s.mu.Lock()` 无感知（假阴性）—— 两条都要修。
5. **保留不变量 3 护栏**作为准入门禁，迁移途中任何一刻它变红即中止。
6. 补 nightly 长跑死锁压测（10min；当前仅 CI 30s 档）。
